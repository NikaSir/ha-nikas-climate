## 3. Реестр функций и допустимое поведение

«Есть в исходнике» означает поддержку программного профиля; «доступно» ниже всегда требует runtime-возможностей установленной сущности.

| Функция | Основание / текущий статус | Правило панели |
|---|---|---|
| Питание, Auto, Cool, Dry, Heat, Fan | Type 8: off=0, auto=1, cool=2, dry=3, heat=4, fan_only=5; `CmdMode` (S05) | Только объявленные `hvac_modes`; off — выключение |
| Уставка | Профиль: 17–30 °C, базовый шаг 1 °C; `CmdTargetTemperature`; runtime min/max/step проверяются отдельно | Не подставлять фиксированный диапазон вместо проверенного |
| Вентилятор Auto/Low/Medium/High | Climate S02; `fan_modes` | Только объявленные значения; не проценты |
| Вертикальное качание | Профиль и поддержка SWING_MODE, затем проверка блока | Один существующий орган управления; включение предпочтительно vertical |
| Горизонтальное качание / both | Есть программные варианты; физическая поддержка точного блока не подтверждена | Не активировать автоматически по одному списку профиля |
| Night / Turbo | Отдельные switch-сущности S03 | Не смешивать с HVAC-режимом, fan speed или preset |
| FRESH / ионизация | Семейство/пульт; локальная команда точного блока не подтверждена | Только реестр «не проверено» |
| CLEAN / самоочистка | Семейство; до 35 минут по руководству | Не активировать до проверки команды и состояния; затем отдельное подтверждение |
| FOLLOW ME | ИК-функция семейства S06/S07 | Не обещать локальную передачу Zigbee-температуры |
| LED / дисплей | В типе 8 есть binary_sensor backlight; управляющего switch нет | Читать полученное состояние; соответствие дисплею и команду проверить на точном блоке |
| Таймеры пульта | Документация семейства | Не объявлять синхронизированными с расписаниями HA |
| SHORT CUT | Память штатного пульта | Будущее избранное HA — отдельные наборы параметров |
| Влажность | Отдельный комнатный датчик HA | Только измерение; целевая влажность не подтверждена |
| Child lock / звук / access control / error | Возможны дополнительные сущности профиля | Диагностика при наличии, без новых кнопок записи |
| ECO / GEAR / +8 °C / Quiet / Breeze Away | Для точных блоков не подтверждены | Не добавлять активные функции |
| Энергия / мощность / компрессорная частота | Источник измерения не установлен | Не вычислять и не имитировать телеметрию |

## 4. Три независимые температуры

| Значение | Источник | Недопустимая подмена |
|---|---|---|
| Температура помещения | Выбранный внешний комнатный датчик HA | Уставка или датчик внутреннего блока |
| Температура у блока | Принятая от кондиционера телеметрия; атрибут current_temperature после проверки происхождения | Оптимистически записанная команда установки температуры |
| Уставка | Подтверждённая цель climate | Использование как измеренной температуры |

Комнатный ярлык/Area связывает сущности **для отображения**, а не передаёт температуру в контур регулирования кондиционера.
Название Virtual Sensor/type 8 не доказывает такую передачу: в исследованной интеграции нет выбора внешнего HA entity как источника температуры для типа 8 (S05).
Внешний надзорный регулятор HA и FOLLOW ME — разные механизмы; ни один не реализуется этим документом.
При отсутствии выбранного датчика выводить «— / Нет данных» и его источник в диагностике. Не переключаться незаметно на другой датчик.
План выбора: целевой комнатный ярлык → проверенное эффективное помещение → разрешённый явный fallback; несколько кандидатов означают неоднозначность.
Эффективное помещение учитывает привязку entity и device. Общие ярлыки вроде мониторинга не являются достаточным основанием.
`null`, пустая строка, unknown/unavailable и нечисловые данные не равны нулю. Ноль допускается только как реальное числовое показание.
Температуру и влажность следует проверять независимо; единица «%» сама по себе не определяет влажность.

## 5. Подтверждение команд: служба, транспорт, состояние

В исследованном S02 setter температуры после отправки присваивает уставку `_current_temp`, а не `_target_temp` ([строки 197–203](https://github.com/DeKaN/ha-syncleo/blob/4f9e15bdaa3d02ff0f08fb7249ac000a4cc52638/custom_components/syncleo/climate.py#L197-L203)); принятые значения обрабатываются раздельно ([строки 153–159](https://github.com/DeKaN/ha-syncleo/blob/4f9e15bdaa3d02ff0f08fb7249ac000a4cc52638/custom_components/syncleo/climate.py#L153-L159)).
Setters режима, вентилятора и переключателей также способны публиковать оптимистическое состояние (S02/S03).
Стандартное включение `async_turn_on()` выбирает AUTO. Для панели, избранного и расписания отправлять явно выбранный пользователем режим; «вернуть последний режим» требует отдельной памяти по устройству.
Начальные значения OFF/False отдельных сущностей не доказывают получение таких состояний от блока.
В S04 `send_command()` возвращает после постановки кадра на отправку; он не ждёт ACK или телеметрии.
При отключённом соединении эта функция пишет предупреждение и возвращает без исключения: успешный вызов HA не равен отправленной команде.
ACK подтверждает приём транспортного кадра, но сам по себе не подтверждает изменение нужного параметра.
`_last_activity` обновляется и при TX, и при RX; это не timestamp последнего принятого состояния.

**Предлагаемая модель, ещё не реализована:**

1. Зафиксировать устройство, допустимые изменения, исходные значения и момент начала операции.
2. Перед каждой записью заново проверить доступность, объявленные возможности и принадлежность сущностей устройству.
3. Отправлять только изменённые допустимые поля: режим → уставка → вентилятор → Night/Turbo → створка. Для цели off не продолжать ненужные записи, способные изменить поведение выключенного блока.
4. Различать результат службы, транспортную отправку/ACK и новую телеметрию нужного поля после команды.
5. Считать «подтверждено устройством» только свежий соответствующий RX-результат; такой сигнал сначала должен предоставить интеграционный слой.
6. Если панель видит лишь HA state без признака происхождения, писать «Состояние HA обновлено»; физическое подтверждение считать недоступным.
7. При истечении срока сохранить конкретную неподтверждённую цель, показать причину и не объявлять весь пакет успешным.
8. Не повторять вслепую весь пакет; не воспроизводить CLEAN или другие действия с побочным эффектом без отдельного протокола.

Нужны отдельные признаки `last_rx`, времени и источника обновления поля и результата команды. Это проект диагностического контракта, не существующие гарантированные атрибуты Syncleo.
Нельзя исправить оптимизм интеграции одной проверкой равенства HA state целевому значению.
Совпавшая телеметрия подтверждает сообщённые параметры, а не физическое движение створки или работу компрессора без отдельного сигнала. Отсутствие подтверждения не доказывает, что команда не выполнилась.
Голубое текущее значение должно отражать установленный уровень достоверности; зелёная цель остаётся целью до результата, а не до завершения вызова службы.

## 7. Честные состояния и диагностика

- `hvac_mode` — выбранный режим; `hvac_action` — действие, если интеграция его действительно публикует.
- В исследованной панели hvac_action не используется. «Обогрев» в поле режима не означает доказанную работу компрессора.
- При неизвестном действии показывать «Нет данных»; не выводить его из разницы температур или положения створки.
- Качание — настройка движения; это не измеренная координата заслонки и не датчик физического закрытия корпуса.
- Различать состояние соединения, свежесть измерений и результат последней команды; одно не заменяет другое.
- Старый last_updated при неизменном исправном состоянии не доказывает потерю связи; произвольный TTL по нему не вводить.
- last_reported отмечает запись состояния интеграцией, включая оптимистические записи; он тоже не заменяет время входящего пакета (S12). Обновление RSSI не освежает измерение температуры.
- В диагностике нужны entity/config entry, версия интеграции/профиля при доступности, источники измерений, capabilities и причины недоступности.
- RSSI в исследованной Syncleo предоставляется диагностической сущностью, отключённой по умолчанию; отсутствие атрибута climate не означает отсутствие такой возможности.
- Текущая `nikas-climate-entry-144.js:100` ищет RSSI только в атрибутах climate и не разрешает соседнюю диагностическую sensor-сущность. Исправление этого поиска пока не реализовано.
- Показывать неизвестные binary-состояния как неизвестные. Неполученное OFF не называть подтверждённым выключением.
- Будущий журнал: время, устройство, поле/цель, этап выполнения, наблюдаемое значение, уровень подтверждения и понятная ошибка.
- ИК-пульт односторонний: Wi-Fi-команды не обновляют его экран и память SHORT CUT. Его экран не источник обратной связи.

## 8. Избранное HA — будущая спецификация

**Не реализовано.** Избранное хранится в HA как отдельные пользовательские наборы, не как память пульта.
Набор содержит имя, устройство и только явно выбранные проверенные параметры: режим, уставку, fan, Night/Turbo и допустимое качание.
Не сохранять current_temperature, влажность, last_seen, неизвестные значения или недоступные функции как команды.
Перед запуском показывать отличия от текущего состояния; существующие названия режимов не переименовывать.
Запуск нового составного набора требует подтверждения; обычная настройка отдельных параметров сохраняет текущую кнопку «Применить».
После подтверждения набор проходит тот же последовательный исполнитель с проверкой capabilities и результата каждого поля.
Частичный успех сохраняется явно: выполненные поля не отправляются повторно только потому, что не подтвердилось другое.
Переключение устройства не должно переносить черновик или избранное другого кондиционера.
Размещение проектировать внутри существующего «Управления» с сохранением утверждённой компоновки.

## 9. Расписания HA — будущая спецификация

**Не реализовано.** Это расписания Home Assistant, независимые от TIMER ON/OFF штатного пульта.
Хранить на сервере HA с версией записи и устойчивой привязкой к устройству; не в браузере и не по частичному совпадению имени. Исполнение работает при закрытом браузере. Подпись — «Исполняет Home Assistant».
Сущность Schedule HA может задавать временные окна (S09); исполнение команд и описанные ниже политики требуют отдельной реализации.
Расписание содержит имя, устройство, проверенный набор параметров, дни/время, часовой пояс HA, признак включения и политику пропусков.
Показывать следующее исполнение, плановое/фактическое время последней попытки и результат по полям. Для отложенного включения/выключения сохранять конкретную дату и время, поддерживать отмену и смену версии.
Сохранение/включение или изменение активного расписания требует подтверждения конкретного расписания; каждое штатное срабатывание не запрашивает новый диалог.
Предлагаемая политика первой версии: пропущенные запуски после остановки HA, отсутствия связи или отключения расписания **не догоняются**.
Пропуск фиксируется с причиной. Старая команда не должна неожиданно исполниться после восстановления связи.
При запуске HA сначала восстановить учёт исполнения и актуальное состояние; не запускать все прошедшие записи.
Для одного кондиционера действует единый последовательный исполнитель ручных пакетов и расписаний.
Ручное действие имеет приоритет: отменяет ещё не начатый конфликтующий пакет расписания; уже отправленное действие отражается в результате.
Не выполнять два разнонаправленных набора одновременно. Конфликт одинакового времени выявлять при настройке и запрещать до разрешения.
Режим queued в HA упорядочивает вызовы (S10), но сам по себе не решает устаревание, отмену и конфликты; это отдельная логика.
Для защиты от повторов сохранять ключ «расписание + версия + плановое время + устройство» и этап попытки. После сбоя между отправкой и записью результата сначала сверять состояние; один ключ не гарантирует ровно одно физическое выполнение при сетевой неопределённости.
При переходе времени несуществующий момент пропускается; повторяющийся локальный момент выполняется один раз по выбранной политике HA/проекта.
Недоступность, unsupported capability или отсутствие подтверждения прекращают соответствующий пакет с понятным результатом, без бесконечных повторов.
Будущий CLEAN исключён из обычных температурных расписаний до отдельной проверки команды, обратной связи и политики остановки.
Перед отправкой повторно проверять отмену и версию расписания. При одновременном редактировании двумя клиентами конфликт версии должен быть видимым.
Helper timer с restore восстанавливает состояние, но не вызывает timer.finished после старта, если таймер истёк при выключенном HA (S11). Нужен отдельный учёт пропусков, а не одна подписка на это событие.

## 10. Очерёдность и критерии приёмки

1. **Источник данных:** P01/P02/P03; зафиксировать точные блоки и установленные версии, сохранить внешний датчик только как источник измерения.
2. **Достоверность и запись:** P04/P05/P06/P07/P08/P09; отдельно исправить подтверждённые upstream-дефекты после сверки установленного кода.
3. **Диагностика:** RX/ACK/optimistic, capabilities, mode/action, RSSI и журнал без обещания несуществующих атрибутов.
4. **Новые функции:** избранное и расписания только после устойчивого исполнителя; FRESH/CLEAN/FOLLOW ME остаются выключенными до отдельной проверки.
5. **UI:** сохранить четыре вкладки, плашку на Сводке, текущие органы управления и фиксированные Header/footer.

| Проверка | Ожидаемый результат |
|---|---|
| Общий ярлык, два кандидата, Area только у device | Правильный явный выбор либо видимая неоднозначность; никакого первого случайного sensor |
| Battery % рядом с humidity; выбранный датчик unavailable/null | Батарея не влажность; измерение отсутствует, подмены и фиктивного нуля нет |
| Night/Turbo/swing unknown; блок offline | Нет ложных Вкл./Выкл.; записи offline не отправляются |
| Служба успешна, RX отсутствует; только optimistic HA update | Нет записи «подтверждено устройством»; конкретная цель остаётся неподтверждённой |
| ACK без нужного состояния; поздний RX; изменение другого поля | ACK и чужое поле не подтверждают цель; поздний подходящий RX учитывается явно |
| Пустые capabilities; swing неизвестен и затем обновляется | Недопустимые команды не уходят; «—» никогда не передаётся в службу |
| Изменение уставки при реальной другой температуре блока | Уставка и измеренная температура сохраняются раздельно |
| Режим heat/cool при action idle/unknown | Режим не объявляется подтверждённой работой компрессора |
| Рестарт HA, потеря связи, повторное событие расписания | Нет неожиданного догоняющего или двойного запуска; причина пропуска видима |
| Ручной пакет и расписание для одного блока | Установленный приоритет, последовательность, отсутствие скрытого перетирания |
| Телефон, четыре вкладки, обновления телеметрии | Существующая геометрия и навигация сохранены; плашка связи только на Сводке |

Аппаратные проверки выполняются отдельно на конкретных блоках; моделирование панели не доказывает исправление прошивки или локального протокола.
Документ завершает исследование и фиксирует критерии будущих изменений; исполняемый код, Home Assistant, расписания и устройства этим изменением не изменены.
